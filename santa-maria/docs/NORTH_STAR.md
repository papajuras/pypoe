# PoE Build-Idea Knowledge Base — North Star

## Purpose

Give an LLM a way to explore the space of Path of Exile mechanics —
items, skills, passives, ascendancies, atlas mechanics, modifiers,
granted effects — **without reconstructing the game's mechanics from
pretraining or from raw text**.

The immediate goal is not to calculate complete builds. It's to enable
an LLM to repeatedly query the knowledge base as a tool and use the
returned mechanical facts and relationships to generate a large number
of **mechanically grounded candidate build ideas** (target: ~100 per
generation run).

The system must keep four things distinct and never blur them:

- facts directly supported by source data
- structured interpretations derived from source data
- relationships explicitly represented in the KB
- reasoning generated by the LLM itself

The LLM must not be allowed to silently turn a guess into a fact.

## Non-goal for the current phase

The system will **not** initially evaluate whether a proposed
interaction actually scales: additive vs multiplicative stacking,
caps, diminishing returns, exclusivity of magnitude, conversion order,
or full DPS/EHP math. That's a later evaluation layer (**the Gate**),
out of scope until the generation loop itself proves useful.

The current phase asks one question:

> Can a structured mechanical knowledge base help an LLM discover real
> interactions it would otherwise miss or misrepresent?

## Why this is hard

PoE's data looks like natural language but behaves like a formal
grammar. Lexically near-identical terms can be mechanically unrelated:

- `ignite` (chance to apply) vs `ignited` (condition that a DoT is
  present)
- `bleed` / `bleeding`, `poison` / `poisoned`
- `chance to inflict X` vs `damage while X is active`
- `enemy has X` vs `you inflict X`
- `hit` vs `damage over time`

**Text similarity cannot be the mechanism that determines mechanical
relationships.** Free-text search stays useful for fuzzy name lookup —
never as the authority on whether two mechanics interact.

## Core representation

A flat relational view of modifiers is insufficient. Relationships are
modeled as an explicit **node-edge graph**, implemented in standard
relational tables (nodes + edges, queried via CTEs) rather than a
dedicated graph database, unless that later proves necessary.

**Nodes** represent distinct entities — mechanics, specific uniques,
keystones, tags, and (see below) build archetypes/payoffs. Nodes carry
an explicit `origin`, so the source-vs-interpretation distinction from
Purpose holds at the node level too, not just conceptually:

```
node_id | type (mechanic/item/passive/archetype/...) | origin (source/derived) | payload (stats, conditions, tags)
```

A unique/skill/passive node is `source` — it comes directly from game
data. An archetype/payoff node (e.g. Wardloop, see cluster gating
below) is always `derived` — it's a construction of the KB, built from
noticing that a set of source nodes co-occur meaningfully, not a fact
extracted from the game itself. This distinction must survive into
query responses, not just storage.

**Edges** represent typed, explicit interactions between nodes — this
is the core of the KB, not a secondary index:

```
source_id | target_id | relation_type
```

- **1-hop relations**: `SCALES`, `ENABLES`, `SHARES_STAT`
- **Conversion relations**: `CONVERTS_TO`, `APPLIES_TO`, `GAINED_AS`
  (e.g. Strength → Spell Damage via Iron Will, Spell Damage → Attack
  Damage via Crown of Eyes)
- **Negative relations** (fail-fast, distinct from Step B): `CONFLICTS_WITH`,
  `OVERRIDES`, `MUTUALLY_EXCLUSIVE` — e.g. Avatar of Fire overriding
  non-fire damage. These are hard, deterministic mechanical facts, not
  a soft scaling judgment, so they belong in Step A: they let the
  generator prune a dead end immediately instead of proposing it and
  wasting a cycle.

### Two distinct query patterns over the same graph: path vs conjunction

These solve different problems and are **not substitutes for each
other**:

**Stat bridging (a path).** Some payoffs come from a single value being
transformed through a chain of conversions — e.g. Replica Alberon's
forces flat chaos damage scaled by Strength; Strength alone is
useless for that without a route to `% Attack Damage` or
`% Chaos Damage`. Strength → (via Iron Will) → Spell Damage → (via
Crown of Eyes) → Attack Damage is one value, transformed step by step,
in a specific direction. This is a graph search problem
(shortest/valid path over `CONVERTS_TO`/`APPLIES_TO`/`GAINED_AS`
edges), and doing this search inside the LLM's own reasoning (manually
calling `get_topology` repeatedly, tracking visited nodes, deciding
when a branch is dead) is fragile: a weaker/local model can loop, give
up on a real path too early, burns many tool calls per insight, and
isn't deterministic across runs. This is exactly what a database
should do in one call, deterministically and cheaply — hence
`find_stat_paths` (see Interface below). The LLM is expected to bring
its own pretrained knowledge of *what* stat it needs (e.g. "flat
attack damage needs increased attack damage to scale") — the database
only answers *how to connect point A to point B*.

**Cluster / gating requirements (a conjunction, not a path).** Some
payoffs are gated behind a **set** of independent mechanics that must
all be present simultaneously, where no single value flows through
them in sequence and each piece is individually inert on its own —
e.g. Wardloop needs cast-on-damage-taken + self-damage + ward-sustain
together; removing any one collapses the whole concept, and there's no
meaningful order between them. A payoff/archetype **node** with
multiple incoming `REQUIRES` edges represents this; querying it must
return the **whole requirement set at once**, not one neighbor at a
time. A tool that only walks the graph neighbor-by-neighbor, or only
finds sequential paths, will systematically miss this pattern — it
needs its own query, not a longer path search.

There is no fixed size for either pattern (a path isn't capped at 3
hops, a cluster isn't capped at 3 requirements) — that was an artifact
of one illustrative example, not a design constraint.

## Data sources

- **RePoE** — raw, game-accurate data (base stats, granted-effect
  tags, drop pools). Primary source for building nodes and generating
  automated edges from shared stat paths (e.g. matching
  `fire_damage_+%`).
- **PoB Community Fork (Lua) — and the "Lua Trap."** The calc engine's
  interpretation is valuable, but writing a robust parser for deeply
  nested, procedural Lua is an unmaintainable anti-goal. In Step A,
  PoB data is used **selectively** (tags, static categories) — it is
  not compiled into an automated ground-truth ontology.
- **Derived / scripted edges** — the actual relationship graph is
  built during ingestion, via scripts mapping RePoE stat paths into
  explicit edges, so the LLM doesn't have to do that deduction on the
  fly at query time.

**Conversion edges must encode completeness, not just existence.**
Iron Will is a 100% conversion of Strength into Spell Damage; other
in-game effects give only partial or conditional conversion. If the
graph doesn't distinguish a full conversion path from a partial one,
`find_stat_paths` can return something technically connected but
mechanically close to useless — the same category of trap as
ignite/ignited, now at the level of conversion edges instead of
lexical similarity. This needs to be captured in the edge data during
ingestion, not discovered later as a bug.

## Interface: the loop's contract with the database

The LLM talks to the KB through a **small, fixed set of narrow
functions**, not free-form SQL — for LLM reliability, not engine
safety. A weaker (eventually local) model is much better at calling a
narrow function than discovering an evolving schema and writing joins.

**The following is a draft direction, not a settled contract.** Per
"query shapes before schema" below, it needs to be checked against
real example queries ("give me an ignite build idea") before it's
treated as fixed:

- **`get_topology(node_id)`** — 1-hop exploration. Returns lightweight
  neighbor IDs + relation types only (no heavy stat payloads).
- **`get_node_details(node_id)`** — deep dive into one node's full
  payload, called only after `get_topology` (or another query below)
  surfaces something worth inspecting.
- **`find_stat_paths(source_stat, target_stat)`** — multi-hop stat
  bridging. Database performs the graph search (recursive CTE) over
  conversion edges and returns an explicit path (or paths), flagged
  with conversion completeness per hop. Depth is a performance-tuning
  parameter, not a fixed design constant.
- **A cluster/requirements query** (name TBD) — given an
  archetype/payoff node, returns its full set of `REQUIRES` edges at
  once, so the LLM sees "this payoff needs A AND B AND C" in a single
  call rather than reconstructing it from repeated 1-hop calls.

**Known gap: discovery.** All four functions above need a starting
node or a pair of known stats. But a generator will sometimes ask
something like "give me interesting things related to ignite" without
knowing a starting node_id at all — entry by concept/tag, not by ID.
No current function covers this. A candidate (`find_by_tag(tag)` or
similar) needs to be added, but — same as the rest of this
interface — only after checking it against real example queries, not
designed from first principles now.

API principles:

- **Evidence-oriented** — response distinguishes DB-supported fact
  from generated explanation.
- **Optimized for the LLM's cognitive cost, not the engine's** — the
  database does the traversal/search work (topology, pathfinding,
  requirement sets); the LLM consumes only the strictly necessary
  nodes per call, and isn't asked to reimplement graph search inside
  its own reasoning.

## Two-step system (only Step A is in scope now)

- **Step A — KB + Generator (current).** Structured data, explicit
  relationships (stat-bridging paths, cluster gating, and
  negative/fail-fast edges), tight context-saving tool interface. LLM
  walks it to produce raw candidate ideas. Noise is acceptable;
  incorrectly asserted mechanics are not.
- **Step B — Gate / Eval (later, conditional on A working).** Checks
  whether a proposed synergy has real mathematical backing —
  multiplicative vs additive, shared caps, diminishing returns.
  Distinct from the negative edges above, which are hard mechanical
  facts, not soft scaling judgments.

## Development principle: query shapes before schema

1. Determine what the generator needs to ask (topology / details /
   stat path / cluster requirements)
2. Define the tool functions
3. Define response contracts (hard limits on payload size)
4. Determine what data those functions require
5. Design the schema around that

Function names and exact shapes above are a starting hypothesis to
test against this process — not the output of it yet.

**Concrete next action:** take 10–20 realistic generator questions
(e.g. "give me an ignite build idea", "how could Strength become
useful for an attack build", "find mechanics that require being
ignited", "can these two mechanics coexist", "what enables this
payoff") and manually trace, per question: which tool → what
parameters → what must the DB know → what response is sufficient.
Finalize the interface from that, not from further up-front design.
This is also where to check a live risk with `get_topology`: a bare
neighbor-id + relation-type response might still force the LLM back
into manual multi-call exploration for cases that deserve a single
richer call — worth confirming against real questions before deciding
whether the response needs more than an adjacency list.

## First validation targets

- **The Ignite Test** — can the KB reliably keep lexically similar,
  mechanically different concepts apart (ignite vs ignited)?
- **The Alberon's Test** — can `find_stat_paths` link a non-obvious
  multi-step stat conversion (Strength → Attack Damage) without
  dumping unrelated items into the prompt, and without the LLM having
  to manually traverse the graph itself?
- **The Iron Will Test** — does the path returned by `find_stat_paths`
  correctly distinguish full conversion from partial/conditional
  conversion, instead of returning a technically-connected but
  mechanically weak path?
- **The Cluster Test** — can a gating/requirements query surface a
  payoff that depends on a *set* of co-present mechanics (e.g.
  Wardloop), none of which would be found by path search alone?
- **The Fail-Fast Test** — does a `CONFLICTS_WITH` edge stop the LLM
  from proposing scaling chaos damage while using Avatar of Fire?

## Success criteria for Step A

1. KB contains real, source-backed mechanical information
2. mechanics aren't represented via text similarity
3. relationships — sequential (stat bridging) and conjunctive (cluster
   gating) alike — are resolved deterministically by the database,
   whether that means a stored edge from ingestion or a value computed
   at query time (e.g. `find_stat_paths` running a CTE over stored
   edges) — never reconstructed ad hoc inside the LLM's own reasoning
4. the LLM can navigate without exceeding context windows
5. candidate ideas trace back to DB-supported facts
6. the generator produces ideas that would be hard to get reliably
   from raw text or model memory alone

## Open questions / next decisions

1. **Tool functions** — verify the draft interface above against real
   example queries; finalize names/shapes only after that.
2. **Conversion edge completeness model** — how "full" vs "partial"
   conversion is captured during ingestion, and how `find_stat_paths`
   surfaces that distinction in its response.
3. **Cluster/requirements query design** — how gating sets are
   authored/derived during ingestion, and what the response shape
   looks like for a multi-requirement payoff.
4. **Pathfinder depth/performance** — recursion limits on
   `find_stat_paths` to keep queries fast; a tuning parameter, not a
   design constant.
5. **Ingestion pipeline** — how to map RePoE `stat_translations` into
   automated `SHARES_STAT` / `SCALES` / `CONVERTS_TO` / `REQUIRES`
   edges during the build step.
6. **Provenance model** — how conflicts between RePoE / PoB / derived
   facts get represented. Deliberately undefined until needed.
7. **`SCALES` may be too coarse.** Strength→Attack Damage (a
   conversion), `% increased fire damage`→ignite damage (a formula
   multiplier), and ignite→damage-while-ignited (unlocking a
   conditional effect) are mechanically different operations currently
   collapsed into one relation type. Whether relation types should
   describe the *nature* of a relationship or the specific *mechanical
   operation* needs an answer before schema design — left open rather
   than solved now.

## Anti-goals

- human-browsable wiki replacement
- exposing free-form SQL to the LLM
- full PoB calc-engine parity or full game simulation
- writing a full Lua parser for PoB's calc engine (the Lua Trap)
- building the Gate before Step A works
- making the LLM reimplement graph search (path-finding or
  requirement-gathering) inside its own reasoning instead of the
  database doing it in one call
- treating stat-bridging paths and cluster gating as the same query
  pattern — they are structurally different and both needed
- dumping full modifier details into topology/path/cluster responses
