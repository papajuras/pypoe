# PoE Build-Idea Knowledge Base — Implementation Plan

## Phase 0 — Minimal schema

Design the smallest SQLite schema required by the first validation tests.

Initial direction:

- `nodes` — `node_id`, `type`, `origin`, `payload` (JSON)
- `edges` — `source_id`, `target_id`, `relation_type`, `provenance`, `completeness` (for conversion edges)

No production optimization, migrations, or full schema design yet.

The schema is allowed to change after real tests expose missing concepts.

## Phase 1 — Real RePoE ingestion

Use a **real RePoE snapshot from the start**. Do not build a fragile slicer.

Load the complete RePoE dataset into the prototype so internal references remain intact and the source representation is preserved. The fact that only a few mechanics are under test does not justify maintaining a partial copy of a highly interconnected source dataset.

At this stage:

- ingest source records into `nodes` without attempting to derive the full relationship graph;
- preserve the original source payload needed for later interpretation;
- keep the ingestion generic enough that expanding coverage does not require redesigning the loader.

Do not broadly integrate PoB yet. Use it selectively only where the first real-data experiments demonstrate that RePoE alone is insufficient.

## Phase 2 — Targeted graph derivation + authored cluster configs

Build small, reusable derivation rules over the real RePoE data, but implement only the relationship types needed for the initial validation targets.

Examples:

- shared stat paths → `SHARES_STAT` / `SCALES`
- conversion mechanics → `CONVERTS_TO` / related conversion edges
- hard conflicts → negative edges
- conversion completeness → full / partial / conditional metadata

Do **not** manually insert individual test edges.

There is one deliberate exception: **cluster/payoff nodes are derived concepts that do not exist in RePoE**. For these, use small authored configuration files describing the intended cluster and its requirements. The ingestion step loads those definitions and creates the corresponding `derived` nodes and `REQUIRES` edges.

For example, a Wardloop-style authored config may declare the payoff and its required mechanics. The config is an explicit piece of derived KB knowledge; it is not presented as raw game-source fact.

This keeps the distinction clear:

- source facts come from RePoE;
- deterministic graph edges are generated by ingestion rules;
- authored payoff/archetype concepts are explicitly marked `derived`.

## Phase 3 — Tool API

Implement the draft interface over the real RePoE-backed graph:

- `search_mechanic(query)` — basic discovery / entry point by mechanic name or equivalent searchable identity;
- `get_topology(node_id)`
- `get_node_details(node_id)`
- `find_stat_paths(source_stat, target_stat)`
- cluster / requirements query

`search_mechanic` is a minimum entry point, not a general search system. Its exact behavior and response shape should be validated against real generator queries rather than expanded speculatively.

Likewise, do not pre-design additional fields for `get_topology` or other responses. Final response contracts should emerge from testing.

## Phase 4 — Real validation

Run the tools through an actual LLM caller (Claude first).

Test at least:

- **Ignite Test** — ignite vs ignited remain mechanically distinct.
- **Alberon's Test** — non-obvious multi-hop stat bridging is found by the database.
- **Iron Will Test** — conversion completeness is represented correctly.
- **Cluster Test** — a conjunctive payoff exposes its complete requirement set.
- **Fail-Fast Test** — deterministic conflicts prevent invalid proposals.

Also test realistic generator questions such as:

> "Give me an ignite build idea."

The goal is not yet ~100 ideas. We only need enough runs to determine whether the interface provides the right information, whether discovery works, and whether the LLM can navigate the graph without excessive traversal or context growth.

## Phase 5 — Iterate

Based on real tests, revise:

- schema
- relation types
- derivation rules
- authored cluster definitions
- tool boundaries
- response shapes

Do not pre-design fields or functions that the tests have not justified.

Particular open risks to evaluate include:

- whether `SCALES` is sufficiently precise;
- whether `get_topology` is sufficient without becoming a heavy response;
- whether `search_mechanic` provides an adequate entry point;
- whether discovery needs to become more capable;
- whether provenance needs more granularity.

## Phase 6 — Expand graph coverage

Only after the small real-data experiment works:

- expand graph-derivation coverage across the RePoE dataset;
- add selective PoB information where justified;
- expand authored cluster/payoff definitions where useful;
- stabilize the graph construction pipeline;
- preserve the validated tool contract unless real evidence requires structural changes.

The full RePoE source dataset is already present from Phase 1; this phase primarily expands **semantic interpretation and relationship coverage**, not raw source loading.

## Phase 7 — Generation loop

Run the actual generation loop over the larger KB and target roughly 100 candidate ideas per run.

Evaluate whether Step A produces a meaningful improvement over raw text/model-memory approaches.

The Gate remains out of scope until Step A demonstrates a relative success.

---

## Core rules

1. **Use real source data from the beginning.** Load the complete RePoE snapshot rather than building a fragile partial-data slicer.
2. **Do not manually invent source facts or individual graph edges.** Derive them from the real source through reusable ingestion rules.
3. **Authored cluster/payoff definitions are allowed and explicit.** They represent derived KB knowledge that does not exist as a native RePoE entity.
4. **Test the interface before optimizing or expanding it.** Query shapes determine the final tool contracts and schema details.
5. **Keep source facts, derived KB knowledge, and LLM reasoning distinguishable.**

## Starting directive for the implementation agent

> Execute this plan step by step. Start with **Phase 0 only**.
>
> Propose **ONLY the SQLite schema** needed for the current North Star and initial validation targets.
>
> Do not write ingestion code (Phase 1), derivation rules or authored configs (Phase 2), or tool/API code (Phase 3) until the schema is reviewed and approved.
